Laser Vision System

Introduction

This is the user manual for the Laser Vision System of Swinburne’s Dysprosium Quantum Gas Microscope Laboratory.

The Laser Vision System is a full-stack solution that consists of a Server, GUI, and multiple Edge computing units.

The Server and GUI facilitate displaying laser deviation readings to lab users.

The Edge computing units are able to run multiple vision processing methods that can each assess laser deviation.

This book can be used as a guide for system installation, system updates, and general operations.

Sections of this book:

  • System Installation
    How to set up the components of this project.
  • System Updating
    How to update the components of this project once deployed.
  • Usage Guides
    How to use the UI stuff.

Server

The server is a rellay point between all the edge compute devices in the lab and gui, it also holds your persistance data such as previously saved device configurations and logs.

Starting the server docker container

navigate to your terminal and run the following command to start the server, listed are the corosponding attributes:

docker run \
-p 8080:8080 \
--name server \ 
--detach \ 
--restart unless-stopped \
--mount type=bind,src=/home/USR/laser-vision-system,dst=/content \
ghcr.io/laser-vision-system/edge:amd64-release-main
-p 8080:8080

this command exposes port 8080 on your host machine and inside the container, how this attribute works is the left most ports dictate what ports the container mouts too on your host where as the right is what the system thinks its being fed on the inside of the container. WE STRONGLY ADVISE AGAINST CHANGING THIS if you do need to change this you can alter the left side to whatever you wish but you must leave the right unchanged e.g. ----:8080, 1234:8080.

–name server

the name of your docker container, this can be changed freely and is the name that will be associated with its container id when you run the command docker container ls

–detach

detaches your terminal from the container when running the container for the first time, the output of the docker run command will provide you with the edge ID and nothing more. if you execute docker container ls you can see the container running in the background

–retsart unless-stopped

ensures that if your docker container stops running for any reason besisdes intentionally stopping it the container will start back up automaticly e.g. on device restart.

–mount…..

this command exposes a folder on your host machine to the inside of the docker container, the src=... portion of the command tells your container where to mount the folder on your host machine. the dst=... is where the files are coming from inside the container. for the command to work You will need to change USR too the name of the lab servers primary account otherwise the logs will not write. if done correctly you will see a server.log file apear inside the laser-vision-system folder in your home directory.

ghcr.io/laser-vision-system/edge:amd64-release-main

ensures that if your docker container stops running for any reason besisdes intentionally stopping it the container will start back up automaticly e.g. on device restart.

camera devices on linux are mounted to the dev folder in a machines root path, this command can be forgone on other platforms but is nessacary for our container to

detaches your terminal from the container when running the container for the first time, the output of the docker run command will provide you with the edge ID and nothing more. if you execute docker container ls you can see the container running in the background

-e …….

the two commands listed that start with the prefix -e are our enviorment varriables and are tailored to our system, SERVER_URL specifies the server address for our system. if not defined on first container run it will default to autoconnect which scans the local network for the server, make sure to include the port when specifying the address which is by default 8080. the seccond varriable is our error logging verbosity VERBOSITY this specifies what level of errors are sent to the server, it ranges from 1 -> 4 with the lower numbers only logging major errors where as 4 will log every occurance on our edge system.

GUI Introduction

The GUI is the graphical user interface of the laser vision system.

It shows the current state of the system and provides ways to interact with it.

GUI Quickstart

The GUI is the frontend of our system where the user can interact and operate the system. The following contents will go through the different sections of the GUI explaining there purpose.

NavBar

The NavBar, short for navigation bar, is used to switch between the different pages of the site. The NavBar icon of the currently selected page shows a red light to indicate which one is currently selected.

From the NavBar, you can swap between the three main pages:

  • Homepage
  • Device Settings
  • Global Settings

Homepage

The Homepage is the main dashboard for the laser vision system. Here, you will find all the information needed for standard operations & monitoring activities.

Alerts

At the top of the page is the alerts section.

It displays important information such as deviation warnings (moderate or high deviations) or device disconnection events. This section can be collapsed if necessary and will show a count of hidden alerts instead.

Main Section

The main body of the page is information about all devices known by the system.

The first tab shows all currently connected devices while the second tab shows devices that have been disconnected or have encountered an issue that prevents them from operating.

Connections

This tab shows all currently connected devices.

The cameras are grouped by the edge computing device that they are connected to.

Each connected camera that has been calibrated will show the current deviation value and be coloured to alert if the deviation has drifted outside a set threshold using a stoplight colour system, where:

Green: deviation within an acceptable range (no alert)
Yellow: deviation within warning zones (moderate severity alert)
Red: deviation within unacceptable ranges (high severity alert)

For each edge computing device, there is a shortcut button to quickly access configuration options for it, sending the user to the device settings page with the corresponding edge device pre-selected when clicked.

You may view more details about a camera by clicking its displayed box. From here, you may calibrate the deviation measurement, configure camera settings via the shortcut button to the device settings page, or view the camera’s live feed.

Disconnections

This tab shows devices that are no longer connected to the system as well as faulty camera devices.

These can include: - Disconnected edge devices - Disconnected cameras - Faulty cameras - Broken cameras: cameras that have connected & initialised but fail to read a frame too many times - Limbo cameras: a connection is detected but the camera cannot be established

Each device has a button to forget the device completely.

Broken cameras have a button to manually force a reconnection attempt.

Limbo cameras only appear briefly before they are classified as broken.

Device Settings

The Device Settings section is for the configuration of the devices used in this project, such as the cameras and microComputers that are currently being used.

Edge Device Settings

Edge devices refer to the Raspberry Pi(s) that is used to run the edge. The edge can also be run on any computer. However, using a microComputer such as the Raspberry Pi is recommended due to its small form factor that fits well in the tightly-packed laser lab.

The connected Edge devices can be configured to:

  • Be selected to filter the specific options for all the connected cameras, displayed in the camera configuration below.
  • Be renamed, allowing the user to give a meaningful identifier to the device.
  • Run a specific vision processing technique. Note: this will select the processing technique for all cameras connected to the microComputer.

Cameras

The cameras that can be configured are the ones that are connected to the system, and have their state as active.

The connected Cameras can be configured to:

  • Rename the selected camera to a more meaningful name (e.g. what it is observing).
  • Change the selected camera controls for tweaks to help improve the vision processing. Some camera controls to consider are:
    • PUT IMPORTANT CAMERA CONTROLS HERE
  • Set the deviation thresholds for the selected camera (e.g. if a camera is misbehaving and needs a custom deviation range to keep it in check).
  • The range (min - max) of the deviation threshold input slider can be configured to suit the needs of the camera’s threshold setup, allowing for fine-tuning of the deviation thresholds.

Global Settings

The Global Settings section is for the configuration of the underlying aspects of the system. It is split into two sections: one for the GUI and the other for the server which includes the default server settings.

GUI settings

The global settings for the GUI include:

  • A toggle for the theme of the user interface, it allows the user to switch between light and dark mode. (Dark mode is recommended.)
  • A toggle for the viewing of the camera feed applicable to the whole application. This helps to declutter the UI.

Server Settings

The global settings for the server defaults include:

  • Web-Socket poll interval is related to the old websocket which was single threaded, the new multi-threaded, this has now been (depreciated).
  • Update Delay is the delay between running the main loop, for faster edge analysis it can be lowered, please note that this will not increase the performance on the edge just the delay between each cycle of analysis. This can be helpful for saving bandwidth over the network at a larger scale, or over long periods of time where image analysis is only needed once every couple of seconds.
  • Camera Error Decrement is the value that is reduce from the internal behaviour counter that each camera has. This decrement occurs when the camera is behaving correctly.
  • Camera Error Increment is the value that the internal behaviour counter increases by. This occurs when the camera is misbehaving.
  • Camera Error Threshold is the limit when passed the system will mark the camera as broken and can be found in the disconnected tab in the homepage.

Vision-CNN Introduction

The vision-cnn repository holds the code for training and running evaluation inference on a Convolutional Neural Network.

This repository uses the dataset-loader repository as a submodule, as well as the datasets hosted on HuggingFace.

The primary method of interacting with this code library is through the included command-line interface (CLI). You can…

  • Train a new model from scratch: cnn train new

  • Resume training (finetune) on an existing model: cnn train resume

  • Run inference on a model: cnn infer

You can use cnn help to see basic command information, cnn help <subcommand> to see detaiked information, and cnn <subcommand> -h for concise usage information.

Train

cnn train

Use cnn train -h to view concise subcommand usage information.

The train subcommand uses the ./output/ directory to save training artefacts and exported model weights. This directory is relative to your current working directory (check with pwd). Each model will get its own folder in this directory, so the folder structure will likely look something like this:

output/
 ├── my_first_model/
 │    └── ...
 ├── model_improved/
 │    └── ...
 ├── model_improved_with_higher_learning_rate/
 │    └── ...
 └── ...

The models folder name is the only required argument when executing each of the training subcommands (new or resume). Attempting to use a name that already exists will fail, unless you use --force or -f.

Both training a new model and resuming/fine-tuning an existing model share a number of common arguments; the full table can be found here.

Training A New Model

cnn train new

Use cnn train new -h to view concise subcommand usage information.

This subcommand has a single required argument, which will be the name of the folder under ./outputs/ that the artefacts and model weights are placed into. E.g. cnn train new model_1 will output into the folder at ./outputs/model_1/.

After executing the command, a textual user interface will appear which displays training progress and metrics. The first time you run the command, it may take a while before the training actually begins, this is the the program automatically tuning itself to your hardware.

Once the training has completed, a summary of the model struture and training metrics will be printed to the terminal. If you included the --evaluate argument (highly recommended), the program with automatically run the evaluation procedure, printing a summary of the result to the terminal and saving more detailed information to ./reports/.

Resuming/Fine-tuning An Existing Model

cnn train resume

Use cnn train resume -h to view concise subcommand usage information.

This subcommand has a single required argument, which will be the name of the folder under ./outputs/ that the model is loaded and resumed from.

By default, the resume subcommand will output directly back into the model folder that it loaded from. This can be changed by using --output <new_model_folder> or just -o <new_model_folder>. E.g. cnn train resume model_1 -o model_1-prime.

Arguments

Both cnn train new and cnn train resume share a large number of arguments. For simplicity, they are all listed here.

They are also viewable with either cnn help train new or cnn help train resume.

Running Evaluation Inference On A Model

cnn infer

Use cnn infer -h to view concise subcommand usage information.

This subcommand has a single required argument, which will be the name of the folder under ./outputs/ that the model is loaded to run inference on.

If the model weights file itself has a name different to model.bpk, you can optionally specify it with --name.

You can choose which dataset to run inference on with --dataset or -d. The options that you can choose from are listed with cnn infer -h.

By default, inference will only run on a single sample, you can choose a different number with --num-samples.

If you wish to perform a full evaluation, you can use the --evaluate-all argument. You are required to also include --report-dir to specify a place to save the output of the evaluation. If the output folder already exists, you must use --force or -f to replace it.

You can configure the evaluation with --evaluation-batch-size and --evaluation-split.

Glossary

GUI
The thing that goes on your browser.
Server
The software that is deployed to the server hardware.
Edge
The software that is deployed to a Raspberry Pi.
Dataset Assistant
A utility program to automate data collection.
CLI
Command-Line Interface.
Argument
In the context of running a command in the terminal, arguments are any other text that follows the name of the executable.
E.g. my_exec --argument --key value
Environment Variable
A key value pair defined on the operating system that is given to a program when it executes.
E.g. KEY=value my_exec
Thread
A single chain of CPU instructions. A program can use multiple threads to run different operations in parallel.
